# 七级 · 项目复现与可玩切片

**成稿格式。** 用阶段验收表展示各阶段，再用分支或对照表说明切片中的两条合法选择。在成稿中实际给出图或表，哪怕只有两三行。正文解释图表能支持的取舍。

写完整拆解案时，先交付「游戏概览与可比作品」，用一句话介绍品类和玩家目标，用短流程说明一次典型游玩，再用小表给出有依据的可比对象、共同点、关键差异及其与本案的关系，最后限定版本、样本与主问题。单局部或已有上下文的续拆只补会影响判断的背景。

把前序分析转成可以分工、集成和验收的开发方案。先定参考版本、目标玩家、目标体验片段、交付平台与已知的人力和时间。自有或获授权的项目按指定范围规划高保真复现。研究其他作品时，保留关键决策、规则关系与体验节奏，用原创内容和实现承载。项目资料不足时，先按已知范围给出顺序，标明会改变排期或验收的未知项。

## 1. 把已有分析变成复现基线

按需取用前序产物，把能够影响交付的结论挂到开发项和验收用例上。

| 分析输入 | 转成开发与验收依据 |
|---|---|
| 玩家体验、注意力与决策 | 当时可见的信息、可行选项、操作时点和反馈。确定界面与试玩观察什么。 |
| 机制解释与设计判断 | 要保住的选择和后果、被对照支持的条件。确定哪些表现必须对齐、哪些可以调整。 |
| 系统逆推、还原与耦合 | 状态归属、输入输出、结算顺序、共享资源、替代路径和触发条件。确定关键依赖和集成用例。 |
| 全局结构与循环 | 阶段交接、正常路径、失败补救、结算和下一轮反馈。确定切片入口、出口和必须跨过的阶段。 |
| 意图模型与竞争解释 | 优先保护的取舍、待核假设和最能区分解释的局面。确定哪些未知项要先验证。 |

为关键项写「来源与版本 → 要保住的行为或体验 → 实现依赖 → 验收用例」。将观察到的结果、规则推导、设计假设和暂定实现标在对应项上。测试夹具可直接设置初态来隔离已知规则。用临时数值接通流程时，保留已知的因果方向，并把该用例标成集成验证。关键结果依赖临时值时，保真验收留待参考参数明确后再跑。缺少前序产物时，只补影响范围、关键依赖或验收的缺口。按待核项是否改变关键选项、代价或状态交接决定先查、试做或后置。

## 2. 先定义一段代表性可玩切片

从全局图选一段能让核心取舍出现并兑现的路径。写清**从什么状态开始 → 玩家在何时看到什么 → 能选什么 → 怎样结算 → 到哪里结束或进入下一轮**。给足以表现差异的代表性起点，覆盖主要路径及一个会改变判断的门槛、失败或补救分支。指定必须接入的系统、可用占位或简化的内容，以及后置的内容。优先保留能改变玩法结果的连接，再补内容数量与表现。

若核心价值来自前一次选择改变后一次机会，优先做一组可以执行的对照。固定可比初态、公共随机条件和对手回应，先核对两条选择各自合法，再追到后续具体哪项动作变得可行、不可行、成本更高或必须换路。用夹具固定补给、牌池或对手时，在完整循环中另验正式规则如何产生这些状态。

给出切片的目标试玩对象、启动方式或计划中的进入入口、试完的收束条件。用一个完整场景定义切片，内部可以做多个固定起点，便于复测同一条规则或换一种玩家选择。

## 3. 从 MVP 到 Demo 安排交付

| 阶段 | 最小交付 | 过关条件 |
|---|---|---|
| **MVP** | 固定初态、占位界面和一项核心选择，优先打通关键状态与结算。 | 同一初态下能逐项核对选项、费用与结果。需要支撑核心取舍的规则偏差有下一步核查。 |
| **完整可玩循环** | 接通准备、行动、结算和下一轮，把决定下游选项的资源、门槛与补救接入同一版本。 | 一条正常路径和代表性异常路径能走通，上一段结果会改变下一段的选项、代价或计划。 |
| **代表性可玩切片** | 用小段原创或自有内容把操作、界面、信息时机和反馈接起来，让目标玩家从指定入口走到出口。 | 分开核对规则效果和玩家行为。玩家在可行动时读到关键信息，作出可解释的选择，并能从反馈理解后果。 |
| **Demo** | 固定展示范围，补齐必要引导、体验节奏、集成回归和构建入口。 | 目标平台上能从启动到正常结束并再次运行。关键验收项有实测记录，剩余偏差有明确处置。 |

用户要求从 MVP 到 Demo 的计划时，成稿固定列出四个独立阶段：MVP、完整可玩循环、代表性可玩切片、Demo。每一阶段分别给最小交付与过关条件。执行时可以共用一个构建或里程碑，展示中保留四个验收门槛。代表性可玩切片必须独立写出入口初态、两条可选路径、结算与后续影响、结束条件和试玩验收。只问其中一个阶段时，按用户圈定的范围回答。先分清目标 Demo 的最小交付和选定参考版本的完整复现范围。只要求验证核心玩法时，按动机和依赖决定哪些模式留在 Demo，完整复现另按约定范围验收。给出首批可开工任务，分别写明交付物、前置依赖、负责角色、集成点与验收项。没有人力或工期数据时按依赖给顺序和可并行项，估算写明前提。

## 4. 用计划、组织、协调、控制保证落地

- **计划。** 从 Demo 和切片验收倒推关键路径，优先试做最可能推翻核心取舍或拖住集成的未知项。时间不足时先减范围，保留核心决策及其后果。
- **组织。** 按可玩的交付分工，明确规则基线、实现、界面、用例和构建由谁负责、由谁验收。单人项目可以兼任。
- **协调。** 相连系统约定输入输出、状态读写者、结算时点和失败时的返回。可用固定数据的任务先并行，关键路径尽早合入同一可玩版本，用同一参考局面检查交接。
- **控制。** 每道验收记录构建、实测结果与偏差。按偏差是否破坏关键选择、跨阶段反馈或交付运行决定修复、接受或后置。规则更新时同步基线、受影响的任务和需重跑的用例。

## 5. 写成可跑的验收用例

对核心用例写明「阶段、对应证据、版本和初态、可见信息、操作、预期结果、实测状态」。规则用例核对状态、结算与跨系统反馈。体验用例观察玩家在决策前理解了什么、怎样选、怎样理解结果。构建用例核对启动、可重复游玩与结束。阈值只有在参考材料或项目要求支持时采用。暂无实测时标为待验证，并指出哪项结果会改变范围或计划。

默认交付复现基线、切片规格、按依赖排列的里程碑、可开工任务与验收表。按用户指定范围交付方案或继续执行。

## 图示与图表

用阶段验收表或里程碑图表示依赖和过关点，并画出可玩切片的决策分支与结算路径。涉及系统、玩法或设计判断的段落应配能说明关系的图或表。一个简单表或流程足以表达时直接用它。图示表达同一组证据和判断，推演与待验证的连接标明状态。
